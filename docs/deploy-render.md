# Deploying the demo to Render

Free, and no card. One web service and one Postgres, both on the free plan, both
described in [`render.yaml`](../render.yaml) so the deployment is something you
can read rather than a set of clicks somebody remembers making.

## Before you start

Two facts about the free plan, because both are easier to accept up front than
to discover during a presentation:

- **The service sleeps** after 15 minutes without a request, and takes about a
  minute to wake. Open the URL ten minutes before you show it to anyone.
- **The free database is deleted 30 days after it is created**, with a 14-day
  grace period to upgrade first. Write the date on a calendar. If the demo needs
  to outlive that, point `DATABASE_URL` at an external Postgres whose free tier
  does not expire, or put the database on a paid plan — nothing else changes.

## Deploy

1. Push this repository to GitHub.
2. In Render: **New → Blueprint**, pick the repository. It reads `render.yaml`.
3. Render asks for the four `ORGANIZATION_*` values. Fill them in — the
   letterhead on the donation certificates comes from there, and an
   unconfigured deployment prints `00.000.000/0000-00` onto a document handed to
   a hospital. Everything else is generated or wired automatically.
4. Approve. The first build takes a few minutes: it compiles Elixir and builds
   the assets inside the image.

That is the whole deployment. There is no separate step to run the migrations or
load the data.

## Which branch, and when it redeploys

`main`, and only when CI is green — both stated in `render.yaml` rather than
left to Render's defaults, which would have been the repository's default branch
and *every* commit.

`autoDeployTrigger: checksPass` means a commit has to pass the GitHub Actions
run — formatter, unused deps, advisories, warnings-as-errors, Credo strict,
Sobelow, 829 tests — before Render serves it. A red commit never reaches the
demo.

**On the day of a presentation, set it to `off`** (or pause the service in the
dashboard). A redeploy compiles Elixir and rebuilds the assets, which takes
minutes, and the free plan runs one instance — so an absent-minded push takes
the demo down while it builds.

## What happens on the first boot

`rel/entrypoint.sh` runs three things, in this order:

1. `EstoqueOS.Release.migrate()` — with `set -e`, so a deploy that cannot
   migrate exits and is reported as failed, rather than coming up healthy and
   serving the old schema.
2. `EstoqueOS.Release.seed_if_empty()` — the catalog and the demo scenario, but
   only when `SEED_ON_EMPTY` is set *and* the `users` table is empty. Both
   guards matter: the free plan gives no shell, so this is the only moment the
   data can be loaded, and it must not happen twice.
3. The web server.

The build log prints what the scenario created and the account to log in with.
Find it in **Logs** on the first deploy — or read it here:
`admin@exemplo.org`, password `demonstracao2026`.

**Change that password immediately** (`/users/settings`). It is written in this
file, which is public.

## Then run the acceptance tests

[`docs/production-acceptance.html`](production-acceptance.html) — fifty tests in
the order they have to happen. Test T-11 is where you create the accounts for
everyone else.

## Configuration

Everything the blueprint sets, and why:

| Variable | Set to | |
|---|---|---|
| `SECRET_KEY_BASE` | you paste `mix phx.gen.secret` | see below; rotating it logs everybody out |
| `DATABASE_URL` | the database's internal connection string | same region, private network |
| `DATABASE_SSL_VERIFY` | `none` | see below |
| `SEED_ON_EMPTY` | `true` | first-boot data loading |
| `POOL_SIZE` | `2` | suits a free database |
| `ORGANIZATION_*` | you fill these in | the certificate letterhead |
| `PHX_HOST` | *unset* | falls back to `RENDER_EXTERNAL_HOSTNAME` |

`PHX_HOST` is deliberately absent. Getting it wrong is the classic cause of a
LiveView that renders once and then never updates, because `check_origin`
refuses a socket from a host the endpoint does not believe it is; reading
Render's own variable removes the chance of typing it wrong. Set it explicitly
only for a custom domain.

### Why `SECRET_KEY_BASE` is not generated by Render

`generateValue: true` would be the obvious choice and it is wrong here: Render's
generated value is shorter than the 64 bytes Phoenix's cookie store requires.

The failure is nastier than a boot error. The app starts, migrates, serves — and
answers *every* request with

    ** (ArgumentError) cookie store expects conn.secret_key_base
       to be at least 64 bytes

so the health check never passes, the deploy reports `update_failed`, and the
logs read as though the application is healthy. Generate the value with
`mix phx.gen.secret`, which produces exactly 64 bytes, and paste it when Render
asks.

### About `DATABASE_SSL_VERIFY=none`

The connection is encrypted. The certificate is not checked. It is a narrow,
deliberate trade for the private network between the service and its own
database, and the app writes a warning on every boot so it cannot quietly become
the permanent arrangement by accident.

It is also not a choice between this and something stricter on the same URL, and
believing otherwise cost two failed deploys on 2026-08-20. Raising it to
`DATABASE_SSL_VERIFY=ca` died at the first query:

    Postgrex.Protocol failed to connect: ssl connect: TLS client:
    ... CLIENT ALERT: Fatal - Bad Certificate — selfsigned_peer
    [error] Could not create schema migrations table

`selfsigned_peer` is the whole story. Render fronts the **external** endpoint
with a proxy holding a genuine Let's Encrypt certificate — verify-full passes
against it, checked the same day:

```bash
openssl s_client -starttls postgres -verify_hostname dpg-….virginia-postgres.render.com \
  -connect dpg-….virginia-postgres.render.com:5432
# issuer: Let's Encrypt YR2 · SAN *.virginia-postgres.render.com · Verify return code: 0 (ok)
```

The **internal** URL the blueprint wires in is answered by the database itself,
with a self-signed certificate no public authority signed. `verify_peer` cannot
pass over it however far the hostname check is relaxed, so `ca` is not a softer
`full` here — it is equally impossible. There is no CA bundle to download; the
line in this file that used to say there was, was wrong.

So there are exactly two honest arrangements:

- **private network, unverified** (what the blueprint does): encrypted, nobody
  checked who answered, one warning per boot.
- **public internet, fully verified**: set `DATABASE_URL` by hand to the
  database's *external* connection string and delete `DATABASE_SSL_VERIFY`. The
  chain and the hostname are both checked, and every query leaves Render's
  network.

`DATABASE_SSL_VERIFY=ca` with `DATABASE_CA_CERT_FILE` under **Environment →
Secret Files** remains the right answer for a provider that publishes a private
CA. Render is not one.

## Loading data by hand, if you ever need to

The free plan has no shell, but the release binary runs anywhere — including
your laptop, pointed at the deployed database. Take the **external** connection
string from the Render dashboard:

```bash
MIX_ENV=prod mix release --overwrite

DATABASE_URL="<external connection string>" \
SECRET_KEY_BASE="$(mix phx.gen.secret)" \
  _build/prod/rel/estoque_os/bin/estoque_os eval 'EstoqueOS.Release.seed()'
```

The external string requires TLS, so leave the SSL settings at their defaults
here. `seed/0` is safe to run more than once; `demo/0` refuses to run twice,
because running it again would double every balance.

## Checking the image before you deploy it

The release builds its own assets, so the whole thing is testable on a laptop —
which is how this configuration was verified rather than hoped:

```bash
docker build -t estoque-os .

docker run --rm --network host \
  -e SECRET_KEY_BASE="$(mix phx.gen.secret)" \
  -e DATABASE_URL="ecto://postgres:postgres@localhost:5433/estoque_os_docker" \
  -e DATABASE_SSL=false \
  -e SEED_ON_EMPTY=true \
  -e PHX_HOST=localhost -e PORT=4021 \
  estoque-os
```

`DATABASE_SSL=false` exists for exactly this and nothing else: a local Postgres
does not speak TLS. It is not a production setting, and the app says so on boot.

## Somewhere other than Render

The `Dockerfile` is the whole deployment contract — pinned to the same Elixir
and Erlang the tests run on, and published for both amd64 and arm64. Anything
that runs a container runs this: Fly.io, Koyeb, a VPS with Docker Compose, an
ARM instance on Oracle Cloud. What is Render-specific is only `render.yaml` and
the `RENDER_EXTERNAL_HOSTNAME` fallback; elsewhere, set `PHX_HOST` yourself.
